# Implementation Plan: MediPath (메디패스) · 증상 기반 진료과·병원 안내 서비스

> 기준 문서: `SPEC.md` v1.0 · 태스크 상세: `tasks/todo.md`
> 기간: 2026-11-11(수) ~ 2026-12-24(목) 발표, 약 6주 · 팀 2명(A: 서비스 트랙, B: 데이터·AI 트랙)

## Overview

6주를 4단계로 나눕니다. ① 1주차에 저장소, API 계약, 데이터를 깔아 두고 ② 2주차에는 두 사람이 계약만 보고 완전히 병렬로 개발합니다. ③ 3주차에 합쳐서 **공개 URL에서 동작하는 MVP**를 만들고 ④ 4~5주차에 파인튜닝과 데이터 파이프라인으로 "데이터 트랙" 요소를 채웁니다. 마지막 주는 기능 동결 후 안정화와 발표 준비에 씁니다.

**핵심 원칙: 3주차 끝(12/1)에 이미 발표 가능한 MVP가 있어야 합니다.** 그 이후 작업이 늦어지더라도 발표가 무너지지 않습니다.

## Architecture Decisions

| 결정 | 이유 |
|---|---|
| 모노레포 1개 | 2명이 계약(OpenAPI)과 compose를 한 곳에서 맞추기 쉽습니다. |
| 계약 우선(Contract-first) | 프론트는 Mock(MSW)으로, 백엔드는 stub 클라이언트로 개발해 서로 기다리지 않습니다. |
| ml-service(FastAPI) 분리 | B가 모델을 교체해도 A의 백엔드 코드와 배포에 영향이 없습니다. |
| `LLMProvider` 인터페이스 | Gemini와 로컬 LoRA 모델을 평가 결과에 따라 교체할 수 있습니다. |
| 분류 모델은 BERT급(CPU 추론) | 공개 URL 운영에 GPU 서버가 필요 없습니다. |
| compose 프로필 `core` / `pipeline` | 배포 VM은 작게 유지하고, 무거운 파이프라인은 필요할 때만 켭니다. |

## 병렬 작업 규칙 (AI 코딩용)

1. **태스크 1개 = 브랜치 1개 = PR 1개.** 브랜치 이름은 `feat/<module-id>/T<번호>-<설명>` 형식입니다.
2. 에이전트에게는 항상 `tasks/todo.md`의 태스크 번호로 지시합니다. 예: "T21을 구현해줘. 수락 기준을 모두 만족하고 검증 명령을 실행해."
   agent-skills의 `/build` 명령을 쓰면 `incremental-implementation`과 `test-driven-development` 스킬을 따라 작업합니다.
3. 에이전트는 자기 모듈 폴더만 수정합니다. `AGENTS.md`와 `CLAUDE.md`에 이 규칙을 명시합니다(T00).
4. `contracts/openapi.yaml`이나 `infra/docker-compose.yml`을 바꾸는 PR은 **반드시 상대방이 리뷰**합니다.
5. PR 전에 에이전트로 `/review`(agent-skills code-reviewer)를 한 번 돌리고, 사람이 최종 확인합니다.
6. 매일 끝날 때 `main`에 머지합니다. 브랜치를 3일 넘게 두지 않습니다.

## Risks and Mitigations

| 리스크 | 영향 | 대응 |
|---|---|---|
| 저장소를 늦게 만들면 두 사람 코드가 따로 자라서 3주차 통합 때 크게 충돌합니다 | 높음 | **T00에서 첫날 저장소를 만듭니다.** "제작물이 나오면 연결"하는 대신, 빈 뼈대라도 바로 올리고 시작하는 것을 권합니다. 비공개 저장소로 두면 됩니다. |
| AI Hub 데이터 승인이 늦거나 거절될 수 있습니다 | 높음 | 첫날 신청합니다. 대체안으로 Kaggle 영어 데이터 + 증상 사전 번역을 쓰고, T14는 어느 데이터로든 진행할 수 있게 만듭니다. |
| 공공데이터포털 API 승인 지연(보통 즉시~수일) | 낮음 | MVP 병원 검색은 Kakao로 바꿔 영향이 4~5주차(T60)로 줄었습니다. T03에서 미리 신청합니다. |
| Gemini 한국어 의료 품질이 부족할 수 있습니다 | 중간 | T13 평가셋으로 2주차에 수치를 확인합니다. 부족하면 프롬프트를 개선하거나 다른 API, T52 LoRA 모델로 대체합니다. |
| RTX 5060에서 PyTorch가 GPU를 인식하지 못할 수 있습니다 | 중간 | CUDA 12.8 이상(`cu128`) PyTorch 휠을 씁니다. 안 되면 3080 Ti나 Colab으로 학습합니다. |
| 배포 VM 메모리 부족(ES, 파이프라인) | 중간 | ES는 `pipeline` 프로필로 옮겼습니다. `core`만 상시로 띄우고, ES를 켤 때 힙을 512MB~1GB로 제한합니다. |
| 파이프라인 범위가 너무 커질 수 있습니다 | 중간 | MVP(CP2) 이후에만 착수합니다. 도구마다 "실제 쓰임 1개"로 제한합니다(SPEC 5절). |
| 위급 상황을 놓치는 결과 | 높음(안전) | 규칙 기반 + LLM 이중 판정, 회귀 테스트로 재현율 100%를 고정합니다(T15). |
