# T30 후속 C-1: LLM 호출 제한 시간 + p95 재측정

- 날짜: 2026-11-13, 실제 Gemini(기본 `gemini-3.5-flash-lite`, 대체 `gemini-3.1-flash-lite`), 무료 등급(분당 15회)
- 설정: `LLM_TIMEOUT_S=8`(호출 1회 제한), `LLM_CANDIDATE_K=30`, ml-service 재시도 1회
- 도구: `python infra/scripts/measure_triage_latency.py --runs 20 --pause <초>` (첫 메시지 → 결과 응답, 기록에 문장 없음)
- **p95는 nearest-rank**(20회 중 19번째 값). 처음 스크립트는 반올림 때문에 20회일 때 최댓값을 p95로 냈습니다. 아래 표와 `t30-latency.md`를 고친 값으로 다시 적었습니다.

## 동작
| 상황 | 증상 추출·추가 질문 | 설명(explain) |
|---|---|---|
| 기본 모델이 8초 안에 답하지 않음 | 같은 모델 재시도 없이 바로 대체 모델 | 대체 모델 없이 바로 기본 문구 |
| 429(분당 한도) | 바로 대체 모델 | 바로 대체 모델 |
| 5xx | 같은 모델 1회 재시도 후 대체 모델 | 같음 |
| 두 모델 모두 실패 | 추출: 503 + 다시 시도 안내 / 질문: 기본 질문 | 기본 문구 |

- 전환은 원인 코드만 로그에 남깁니다: `llm_fallback from=... to=... cause=429|timeout|5xx`
- **Gemini는 서버 기한(`X-Server-Timeout`)이 10초 미만이면 400으로 거부합니다.** SDK가 클라이언트 제한 시간을 그 헤더로도 보내므로, 헤더는 `max(10, 제한)`으로 따로 넣고 클라이언트는 8초에 끊습니다(실제 API로 확인: 8초 정상, 0.3초 제한은 `ReadTimeout`).

## 결과 (20회씩)

(JSON 안의 `summary.p95_ms`는 고치기 전 계산이라 최댓값입니다. 아래 표는 `runs`에서 nearest-rank로 다시 계산한 값입니다.)

| 시나리오 | 성공 | p50 | **p95** | 최대 | 대체 모델 전환 |
|---|---|---|---|---|---|
| 단독, 20초 간격 (`t30-llm-timeout-alone.json`) | 20/20 | 4.7 s | **6.1 s** | 6.5 s | 0 |
| 연속 호출(간격 0, 분당 한도 초과) (`t30-llm-timeout-burst.json`) | 20/20 | 4.3 s | **5.9 s** | 11.3 s | 23 (모두 429) |

연속 호출 시나리오의 변화(같은 조건, 수정마다 다시 측정):

| 버전 | p50 | p95 | 최대 | 비고 |
|---|---|---|---|---|
| 제한 시간만 추가 | 4.7 s | 8.4 s | 9.1 s | 429 때 설명 4건이 기본 문구로 바뀜(버그) |
| 설명도 429 때 대체 모델 | 4.8 s | 10.4 s | 16.3 s | 429마다 같은 모델 1초 후 재시도 → 지연 |
| **429면 바로 대체 모델(최종)** | 4.3 s | **5.9 s** | 11.3 s | 최대값은 대체 모델의 설명 1건(7.9 s) |

- 두 시나리오 모두 목표(p95 < 10 s)를 만족합니다. 제한 시간(8 s)에 걸린 호출은 이번 측정에서 0건이었고, 꼬리는 주로 429였습니다.
- 남은 꼬리: 대체 모델도 느리면 한 턴이 8 s + 8 s까지 걸릴 수 있습니다. 무료 등급의 한계이며, 배포 후 실제 사용량으로 다시 봅니다.
